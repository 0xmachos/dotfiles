# REVIEW.md

Rulebook for every reviewer of this repository. It is a personal macOS setup:
`bittersweet` (a zsh orchestrator) deploys shell configuration, git hooks,
`bin/` tools and launchd jobs; `./test` is the gate.

## What to flag

Each item is an invariant. A change that breaks one is a finding.

- **Commit-message shape.** The repo is public, so a message is published. A
  subject line says WHAT changed, in the imperative; at most a short body (about
  120 words) that also says only what changed. Flag reasoning, trade-offs,
  session narrative, user quotes, hostnames, network addresses, machine
  nicknames, other repos' names or SHAs, security-posture descriptions and any
  ledger- or session-style trailer (`Co-Authored-By` is allowed). Flag
  `--allow-empty` commits and any code or doc that creates them. The same goes
  for every comment and header block in a tracked file; dated design rationale
  is fine.
- **SHA-256, never MD5.** Flag MD5 used to check a file or compare content, in
  code (`hashlib.md5`, `md5`, `md5sum`, `openssl md5`) or in a command. Use
  `shasum -a 256`, `openssl dgst -sha256` or the language's SHA-256.
- **macOS paths, not XDG paths.** New code that picks a location maps
  `~/.local/bin` to `/usr/local/bin`; `~/.cache` and `$XDG_CACHE_HOME` to
  `~/Library/Caches/<name>`; `~/.config`, `~/.local/share` and `$XDG_*_HOME` to
  `~/Library/Application Support/<name>`. Not findings: a third-party tool's own
  installer path, a genuinely Linux target, and the 1Password wrapper scripts in
  `~/.local/bin` (that directory precedes Homebrew on `PATH`, so they shadow the
  real binaries). Flag scratch data in `/tmp` or `/var/folders`.
- **The three copy exceptions in deployment.** Deployment is symlink-by-default.
  Flag a change that turns any of these back into a symlink: launchd plists (the
  login scan skips symlinks); `jump-system` and `jump-user` (root must not
  execute through a user-writable path; a Documents-folder permission limit);
  `.config/1Password/ssh/agent.toml` (the app does not follow symlinks). Flag a
  new `bin/` tool, plist or top-level file that nothing deploys: `tests/linkage`
  expects an owner for each.
- **Git hooks stay pipeline-free.** Flag a pipeline in a hook (scan targets go
  to temp files; predicates are pure zsh), and a hook in `.githooks/` that does
  not chain to the one in `.config/git/hooks/`.
- **A hook never gains a non-interactive skip.** Flag a new variable, config key
  or flag that lets a non-interactive caller bypass a hook.
- **Build secret-shaped test values at runtime.** Flag a literal secret-,
  address- or identifier-shaped value in a fixture; assemble it by string
  concatenation.
- **Test-suite conventions.** Suites in `tests/` are sourced, never executed.
  Flag `exit` (use `return`), a mode other than 644, a missing entry in the
  `SUITES` array in `./test`, a write outside the `$TMPDIR` sandbox, and an
  order dependence between suites.
- **Generated files are never hand-edited.** `.completions/_bittersweet` is
  regenerated by `./bittersweet completions`. Flag a hand edit, and a new
  subcommand without the array entry, `case` arm and regeneration.
- **Gitignored-by-design paths stay uncommitted.** Flag `git add -f`, a
  `.gitignore` negation, or a newly tracked file under a path the ignore rules
  or `.extra_gitexclude` deliberately hide.
- **Script style.** zsh, extensionless, `set -euo pipefail`, `umask 077`, a
  `main "$@"` entry point, absolute binary paths in anything launchd runs
  (launchd does not source `.zshrc`). `bin/agent-reset` is the one Python file
  and stays stdlib-only.
- **Workflows.** Flag a third-party action not pinned to a full commit SHA with
  the tag in a trailing comment, a missing read-only `permissions` block,
  checkout without `persist-credentials: false`, and any added CI nobody asked
  for.
- **Dependencies.** Added or updated npm packages must leave
  `npm audit signatures --userconfig=/dev/null` passing. Python uses `uv` only:
  flag `pip install`, `venv`, `virtualenv`, `conda`, `pyenv`, or a hardcoded
  `/tmp` where `tempfile` belongs.
- **No secrets in the tree.** Flag a key, token, password or private address in
  any file, comment or fixture.

## Evidence bar

- Cite `file:line` for every finding, at the line that is wrong, not the
  function above it.
- Reproduce before reporting. Run the affected suite (`./test <suite>`) or the
  smallest command that shows the fault, and quote the output. For a claim about
  `bittersweet`, read the function; do not infer from its name.
- Suite map. `bittersweet`, `bin/`, plists or new top-level files: `linkage`.
  A hook under `.config/git/hooks/`: its own suite (`pii-hook`, `message-policy`,
  `git-sign`, `gh-publish`, `git-bypass`). Docs and instruction files: `okf`,
  `agents-md`. Anything under `tests/`: `shellcheck` plus the suite itself.
- A clean clone skips suites that need per-machine inputs, and a skip is not a
  pass. Tie every "passes" claim to the suites that ran, and name the suites you
  did not run and the paths you did not read.
- Search the whole repo before calling something unexplained: header comments
  and `tests/` often carry the reason.
- Report a claim you could not reproduce as unverified, never as a defect.

## Severity

Use exactly these words: `BLOCKER`, `MAJOR`, `MINOR`, `NIT`.

- `BLOCKER`: breaks a hook gate, publishes something that must not be public (a
  secret, a private name, a reasoning-bearing commit message), makes a
  deployment destructive, or weakens a gate so a failing check passes.
- `MAJOR`: a script or suite fails on a clean run, a copy exception reverted to
  a symlink, a new file nothing deploys, MD5 used for integrity, wrong behaviour
  on a likely path, new logic with no test.
- `MINOR`: a convention breach with no behavioural effect, a stale comment on
  load-bearing code.
- `NIT`: wording or preference. Report only if nothing above exists; cap at 3.

## Skip

- Lint that CI already enforces: `shellcheck` (pinned release, bash mode),
  `actionlint`, `zizmor`, `gitleaks` and `plutil -lint`. Report a lint
  suppression only if its justification is wrong.
- Generated files (`.completions/_bittersweet`): review the generator only.
- Formatting, naming taste, spelling variant, comment density.
- Pre-existing problems the diff does not touch (list under "Not in this change").

## Report shape

1. Numbered findings, most severe first. Each carries: severity, `file:line`,
   one sentence stating the defect, the triggering input or state, the evidence
   (command and output), and the smallest fix.
2. "Could not check": suites skipped, files not read, claims left unverified.
3. "Not in this change": pre-existing issues, one line each.
4. A final line, `SHIP` or `NO-SHIP`.

For inline comments, prefix the severity word and put the verdict in the
summary. Do not edit files while reviewing. An empty findings list is valid.
